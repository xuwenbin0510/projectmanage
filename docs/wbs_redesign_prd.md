## 0. 本次分析新增的两项关键发现（先看这里）

主理人给出的 4 点事实我已逐条复核，**全部属实**。在复核过程中我另外挖到 **2 项会直接改变结论的证据**，请优先阅读：

### 发现 ①：模板里早就有 `anchorStage` —— 里程碑本来就是「锚定在阶段上的时间点」

`docs/lifecycle/*.json` 中每个里程碑都带 `anchorStage` + `anchor(start/mid/end)` 字段，但**实例化时被丢弃**：`milestones` 表无 `stage_id` 列，全仓库 `grep anchorStage` 在 `web/src` 下**零命中**。

```
A-delivery（6 阶段 / 7 里程碑）
  M1 项目启动      → S1 立项            anchor=end
  M2 需求基线冻结   → S2 需求            anchor=end
  M3 设计评审通过   → S3 设计            anchor=end
  M4 首件调试完成   → S4 开发与首件调试   anchor=end
  M5 集成测试通过   → S5 集成测试与出厂   anchor=end
  M6 客户验收通过   → S6 交付验收与结项   anchor=mid
  M7 项目结项      → S6 交付验收与结项   anchor=end
```

**这说明设计意图从一开始就是「阶段=区间，里程碑=区间上的锚点」，只是实现时断链了。**

### 发现 ②：里程碑与阶段**不是 1:1**，B/C 类存在「空阶段」和「三里程碑阶段」

| 模板 | 阶段数 | 里程碑数 | 无里程碑的阶段 | 多里程碑的阶段 |
|---|---|---|---|---|
| A-delivery | 6 | 7 | 无 | S6（M6 mid + M7 end） |
| B-product | 4 | 6 | **S2 设计与拆解（0 个）** | S1（M1+M2）、**S4（M4+M5+M6，3 个）** |
| C-infra | 5 | 6 | **S3 施工准备（0 个）** | S4（M3+M4）、S5（M5+M6） |

> **结论：用户「生命周期阶段是不是就是里程碑」的直觉，在 A 类近似成立（6↔7），但在 B/C 类被数据证伪。**
> 若强行合并，B 类的「设计与拆解」阶段会因无里程碑而**丢失质量门 QG2（方案就绪门，ownerRole=tl）**，C 类「施工准备」会丢失 **QG3 开工条件门**。这是硬性质量管控损失，不可接受。

### 发现 ③（附带）：里程碑方向规则是「契约与实现完全相反」，且 DB 有硬约束

主理人事实 3 描述实现行为正确，但**问题比「命名错误」严重**——这不是死代码，是**三层规格互相打架**：

| 层 | 提前（earlier） | 延后（later） | 出处 |
|---|---|---|---|
| 契约 `api-contract.md:1155,1256` | **拒绝** `E_MS_NO_ADVANCE` | `E_MS_NEED_CHANGE` | §7.3 |
| Mock 实现 `mock/index.ts:812-830` | **直接放行** + 审计「日期提前」 | `E_MS_NEED_CHANGE` | 一致 |
| **DB Schema `schema.sql:189`** | **`CHECK (planned_date >= baseline_date)` 物理拒绝** | 允许 | 表约束 |

> 即：用户想要的「可以提前」，**在真实 SQLite/PG 落库时会被 CHECK 约束直接拒绝**，只有 mock 内存态能跑通。另外 `delay_days` 注释写「永远 >= 0」，提前后会变负数，字段语义同步失效。
> **所以事实 3 的「只需清理命名」结论需要修正为：要改契约 + 改 CHECK 约束 + 改 delay_days 语义 + 删错误码，共 4 处。**

### 发现 ④（附带）：两个契约约束在 mock 中根本没实现

| 错误码 | 契约位置 | mock 实现 | 状态 |
|---|---|---|---|
| `E_WBS_PARENT_TYPE` | `api-contract.md:1375,1434,2072` | **零命中**，连 `ErrorCode` 枚举都没有 | 纯契约，未实现 |
| `E_STAGE_SEQUENCE` | `api-contract.md` §5、`types/api.ts:63` 有文案 | **`mock/index.ts` 零命中** | 有文案无逻辑 |

> 用户问「创建时没有顺序限制合理吗」——**答案是：不是设计成不限制，是约束压根没写**。所谓「阶段顺序硬锁」目前也只是文档承诺。

## 2. 三套「阶段」概念厘清

| 维度 | ① 生命周期阶段 `project_stages` | ② 里程碑 `milestones` | ③ WBS stage 节点 `wbs_nodes.nodeType='stage'` |
|---|---|---|---|
| **本质** | **时间区间**（有始有终） | **时间点**（一个日期） | **分解容器**（结构分组，无时间语义） |
| **数据源** | 建项目时按 A/B/C 模板实例化 | 建项目时按模板实例化（向导第 4 步可编辑日期） | 用户在 WBS 页**自由手建** |
| **数量** | A=6 / B=4 / C=5，**固定** | A=7 / B=6 / C=6，**可增删改** | 任意，无上限 |
| **能否手动增删** | ❌ 否（模板锁定） | ✅ 是（`required` 里程碑受 `E_MS_DELETE_REQUIRED` 保护） | ✅ 完全自由 |
| **顺序约束** | 契约称硬锁 `E_STAGE_SEQUENCE`，**实际未实现** | 无（各里程碑独立） | **无**（当前可乱建） |
| **质量门** | ✅ 1 阶段 : 1 门，阶段末硬门控（`quality_gates.stage_id` UNIQUE） | ❌ 无 | ❌ 无 |
| **日期规则** | `started_at`/`finished_at`，随推进写入 | `baseline_date` 永不改 + `planned_date` 单向规则 | `start_date`/`due_date`，自由填 |
| **与其他两者的绑定** | ← 模板中被里程碑 `anchorStage` 引用（**未落库**） | → 模板有 `anchorStage` 指向阶段（**未落库**）；← 被 `wbs_nodes.milestone_id` 引用（**UI 未接**） | → 有 `milestone_id` 外键（**恒 null**）；**与生命周期阶段无任何关联** |
| **归属层** | 治理层（管控 / 门禁） | 治理层（承诺 / 对客节点） | 执行层（干活 / 排期） |

### 关键判断

> **①与②不是重叠，是「区间 vs 点」的互补关系**——阶段回答「现在处于哪个环节、能不能过门」，里程碑回答「哪天必须交出什么、延期要不要走变更」。
> **真正冗余的是 ③ 的命名**：WBS 的 `stage` 只是个分组容器，却占用了「阶段」这个已被 ① 严格定义的词，这才是用户困惑的根源。
> **真正缺失的是绑定**：①②③ 三者在数据模型上是三座孤岛，模板里画好的桥（`anchorStage`）没修。

## 3. 阶段/里程碑关系方案（核心）

### 方案 A：合并 —— 生命周期阶段并入里程碑

| 项 | 说明 |
|---|---|
| 做法 | 废弃 `project_stages`；里程碑增加 `gated: boolean` + `gate_id`，质量门挂到里程碑上；`wbs_nodes` 直接引用 `milestone_id`；顺序由里程碑日期先后隐式表达 |
| 表变化 | 删 1 表（`project_stages`）；`quality_gates.stage_id` → `milestone_id`；`milestones` 加 `gated`/`seq` |
| ✅ 优点 | 概念数从 3 降到 2，用户心智最轻；WBS 只需引用一种东西；契合用户直觉「两者应合一」 |
| ❌ 缺点（致命） | **1. B/C 类会丢门**：B 类 S2「设计与拆解」、C 类 S3「施工准备」**无对应里程碑**，合并后 QG2/QG3 无处安放（见发现②）<br>**2. 语义降维**：阶段是区间（有 `started_at`/`finished_at`、有「当前处于第几阶段」），里程碑是点，合并后「项目现在在哪个阶段」这一核心看板指标失去载体<br>**3. 门禁可被绕过**：里程碑用户**可手动增删**，而门必须不可删——合并后需给里程碑加一堆「这个不能删」的例外，反而更复杂<br>**4. 迁移成本最高**：涉及 `project_stages`/`quality_gates`/`gate_checklist_items`/项目概览/报表多处 |
| 工作量 | 大（约 5 张表 + 概览/报表/门控全链路） |

### 方案 B：保留但绑定 —— 阶段为脊柱，里程碑锚定其上（**推荐**）

| 项 | 说明 |
|---|---|
| 做法 | ① 生命周期阶段仍是唯一 spine（顺序锁 + 质量门）；② `milestones` **补 `stage_id` + `anchor(start/mid/end)`**，把模板里已有的 `anchorStage` 真正落库；③ WBS stage 节点**引用生命周期阶段**（新增 `lifecycle_stage_id`），WBS task/package 仍可挂 `milestone_id` |
| 表变化 | `milestones` +2 列（`stage_id`、`anchor`）；`wbs_nodes` +1 列（`lifecycle_stage_id`，仅 `node_type='stage'` 时有值）；**不删表** |
| ✅ 优点 | **1. 零信息损失**：B/C 的空阶段照常持门，S4 的三个里程碑照常并存（N:1 关系天然支持）<br>**2. 改动最小且有现成设计**：`anchorStage` 已在模板 JSON 里写好，本质是「把断链接上」而非重新设计<br>**3. 语义清晰可讲**：阶段=区间/门禁，里程碑=区间上的承诺点，WBS=区间内的活儿——一句话能对用户解释清楚<br>**4. 解锁强能力**：绑定后可自动算「阶段进度 = 该阶段下 WBS 完成度」「里程碑风险 = 关联 WBS 任务是否延期」「过门前置校验 = 该阶段里程碑是否已达成」 |
| ❌ 缺点 | 概念仍是 3 个（但已从「三座孤岛」变成「一棵树」）；需要在 UI 上做好可视化（阶段泳道 + 里程碑旗标），否则用户仍可能困惑；WBS stage 引用生命周期阶段后，用户建 WBS stage 时需先选归属阶段，多一步操作 |
| 工作量 | 中（2 张表加列 + WBS/里程碑表单 + 概览泳道） |

### 方案 C：维持三套 + 仅 UI 澄清

| 项 | 说明 |
|---|---|
| 做法 | 数据模型不动；只做 ① WBS 层级约束（`E_WBS_PARENT_TYPE`）② UI 文案区分（把 WBS 的 `stage` 改叫「分解分组/工作分区」）③ 补里程碑选择器 |
| ✅ 优点 | 改动最小、风险最低、无迁移；能快速解决 I-1/I-4/I-9 |
| ❌ 缺点 | **概念债原样留存**，用户下次还会问同样的问题；`anchorStage` 继续烂在模板里；阶段进度/里程碑风险等衍生能力全部无法实现；属于「治标」 |
| 工作量 | 小 |

### 📌 推荐：**方案 B（保留但绑定）**

**理由（按权重排序）：**

1. **数据证伪了合并的可行性**——B 类 4 阶段 vs 6 里程碑、C 类 5 vs 6，且存在**零里程碑阶段**与**三里程碑阶段**，N:1 是客观事实，强行做成 1:1 必然丢质量门（发现②）。用户「两者应合一」的直觉来自 A 类的 6↔7 近似巧合，但 A 类恰恰也不是 1:1（S6 挂了 M6+M7）。
2. **方案 B 不是新设计，是补完既有设计**——`anchorStage`/`anchor` 字段已经躺在三份模板 JSON 里，方案 B 的核心工作量就是「把它写进表、显示到 UI」，架构风险极低（发现①）。
3. **区间与点各有不可替代的职责**——门禁必须挂在不可删的区间上，承诺必须落在可协商的点上。里程碑「可手动增删」而阶段「模板锁定」这一现有差异，本身就是两者不能合并的强信号。
4. **方案 C 治标不治本**，用户已明确表达「先解决阶段/里程碑关系，再做层级约束」，纯 UI 澄清不满足其诉求。

**给用户的一句话解释（建议直接用于 UI 引导）：**
> **阶段**是项目走到哪一步（有始有终、走完要过质量门）；**里程碑**是必须在某天交出的成果（对客承诺、延期要走变更）；**WBS** 是为了达成它们要干的活。一个阶段里可以有 0 到 3 个里程碑。

## 4. WBS 层级合法性约束

### 4.1 精确规则（扩展 `E_WBS_PARENT_TYPE`）

| 父节点 | 允许的子节点类型 | 说明 |
|---|---|---|
| **根（`parent_id = NULL`）** | `stage`、`package` | 不允许根级直接建 `task`（散任务无归属） |
| **`stage`** | `package`、`task` | 允许 stage 下直接挂简单 task（不强制中间层） |
| **`package`** | `task` | 工作包下只能是任务 |
| **`task`** | **无（必为叶子）** | 往 task 下挂任何节点 → `E_WBS_PARENT_TYPE` |

**补充规则：**

| 规则 | 内容 | 错误码 |
|---|---|---|
| R-1 | 层级深度上限 **4 层**（根 stage → package → task，含根共 3~4 级） | `E_WBS_DEPTH`（新增，或复用 `E_VALIDATION`） |
| R-2 | `task` 必为叶子，创建/移动时校验目标父类型 | `E_WBS_PARENT_TYPE`（400，`data:{parentNodeType}`） |
| R-3 | 移动（`PUT /move`）同样校验，不只在创建时校验 | `E_WBS_PARENT_TYPE`（契约 `:1434` 已定义） |
| R-4 | 节点**类型不可变更**（已有子节点的 stage 不能改成 task） | `E_WBS_TYPE_LOCKED`（新增） |
| R-5 | 叶子节点必填负责人 + 工时（已有） | `E_WBS_LEAF_INCOMPLETE`（已实现） |
| R-6 | 若采纳方案 B：`stage` 节点必须选归属生命周期阶段 | `E_WBS_STAGE_UNBOUND`（新增） |

### 4.2 B 类（敏捷）是否豁免

**建议：部分豁免，而非全豁免。**

| 规则 | A 类 | B 类（敏捷） | C 类 | 豁免理由 |
|---|---|---|---|---|
| R-2 task 必为叶 | 强制 | **强制**（不豁免） | 强制 | 这是数据完整性底线，与方法论无关；task 下挂 task 会破坏看板叶子聚合与进度 rollup |
| R-1 深度上限 4 层 | 强制 | **放宽到 3 层**（stage→task） | 强制 | 迭代周期短，`package` 中间层多余 |
| 根下不允许 `task` | 强制 | **豁免**（允许根级 task） | 强制 | B 类常见「一个迭代 = 一坨用户故事」平铺，强制建 stage 是仪式负担 |
| R-6 stage 必须绑生命周期阶段 | 强制 | **可选**（允许 unbound） | 强制 | B 类 WBS stage 常按「用户故事分组」而非生命周期阶段 |
| 粒度告警 | ≤5 人日（非阻塞） | ≤2 人日（非阻塞） | ≤5 人日 | 已实现，维持 |

**豁免的实现方式（三选一，建议第 2 种）：**

1. ❌ 代码里散布 `if (type === 'B')` —— 已有先例（`mock/index.ts:455` PO 校验），但会越写越乱
2. ✅ **把层级规则写进 `lifecycle_templates.definition` 的新字段 `wbsRules`**，如 `{"maxDepth":3,"allowRootTask":true,"requireStageBinding":false}`，服务层统一读取——与现有 `granularity` 字段同构，零新机制
3. ❌ 独立配置表 —— 过度设计

## 5. 根节点创建时机

### 现状

| 侧 | 行为 |

| 契约 `api-contract.md:616` | 建项目单事务含「WBS 根节点」 |
| 实现 `WbsPage.tsx:229,237` | 无根节点，EmptyState 提示「点击右上角『新建根节点』开始分解」 |

### 选项对比

| 选项 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| **甲：建项目自动建空根** | 事务内建 1 个 `nodeType='stage'`、name=项目名的根 | 契约不用改；WBS 页永不空白 | 单根会多一层无意义嵌套；用户想要多根时受限 |

### 建议

> **采纳「丙」**，并同步修订 `api-contract.md:616` 为「项目 + 阶段 + 门 + 检查项 + 里程碑（含 stage_id 锚定）+ 看板配置 + **WBS 阶段骨架节点** + 角色任命」。

### 8.2 是否需要双写过渡期

> **建议：不需要双写，但需要「宽松期」。**

理由：本次变更是**加列**而非改语义、删表，新旧数据可共存：

| 阶段 | 策略 |
|---|---|
| **T0 迁移** | 加列 + 模板回填 `milestones.stage_id`（100% 覆盖）+ 重建表去 CHECK |
| **T1 宽松期（建议 2 个迭代）** | `wbs_nodes.lifecycle_stage_id` 与 `milestone_id` **允许为 NULL**，不做阻塞校验，仅 UI 黄色告警提示补全；新建节点走新规则 |
| **T2 收紧** | 对**新建**节点强制 R-6（stage 必须绑定）；存量 NULL 数据保持只读兼容，不批量强制 |
| **回滚** | 加列可直接 `DROP COLUMN`；CHECK 约束重建表操作需保留迁移前 `pm.db` 备份 |

**唯一需要注意的不可逆点**：删除 `CHECK (planned_date >= baseline_date)` 后，一旦有里程碑被提前（`planned_date < baseline_date`），**回滚该 CHECK 会因存量数据违反约束而失败**。建议迁移脚本中记录「首次出现提前记录的时间点」，作为回滚窗口的硬边界。

## 9. 结论

- **主理人给出的 4 点事实全部复核属实**，但事实 3 的处置结论需从「清理命名」升级为「4 处修改 + 3 处连带修正」，因为 DB 层存在物理 CHECK 约束（发现③）。
- **用户「阶段=里程碑」的直觉被模板数据证伪**（B/C 类存在零里程碑阶段与三里程碑阶段），故不建议合并；但用户的困惑真实且合理，根源在于**三者未绑定 + WBS 误用「阶段」一词**。
- **推荐方案 B**：把模板里早已写好、却在实例化时丢失的 `anchorStage` 关系真正落库，让「阶段（区间）→ 里程碑（点）→ WBS（活）」形成一棵树。这是改动量与收益比最优的路径。
- **执行顺序遵从用户意见**：先定阶段/里程碑关系（D-1），再落 WBS 层级约束（§4）。
