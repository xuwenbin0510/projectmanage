## A. 根因：一句话 + 拆解

> **系统把「一件事分几步做」这一个常识，拆成了四层互相引用的概念（生命周期阶段 / 阶段锚点 / 工作分区 / 工作包），却没有给其中任何一层配自动状态推导——于是用户既要额外学四个词，又发现学完之后界面上什么都不会动。**

### A.1 四重概念叠加（用户可见 7 个名词）

| 层 | 概念 | 数据载体 | 用户在哪儿见到 | 实际语义 |
|---|---|---|---|---|
| 1 | **生命周期阶段** | `project_stages` | 概览「生命周期阶段」条、WBS 表单「归属生命周期阶段」、里程碑页「所属阶段」列 | 时间区间 + 质量门载体 |
| 2 | **质量门** | `quality_gates`（1:1 阶段） | 概览阶段条内 | 阶段末检查点 |
| 3 | **里程碑** | `milestones` | 里程碑页 | 时间点 / 对客承诺 |
| 4 | **锚点 start/mid/end** | `milestones.anchor` | 向导第 4 步下拉、里程碑页徽标 | 里程碑落在阶段的起/中/末 |
| 5 | **工作分区** | `wbs_nodes.nodeType='stage'` + `lifecycleStageId` | WBS 树、WBS 表单 | 分解容器（可绑回 1） |
| 6 | **工作包** | `wbs_nodes.nodeType='package'` | WBS 树 | 分解容器 |
| 7 | **任务** | `wbs_nodes.nodeType='task'` | WBS 树、看板 | 干活单元 |

其中 **1 / 4 / 5 / 6 四个概念，用户脑子里都是「阶段/分组」**，系统却要求区分。这是"不好理解"的直接来源。

### A.2 状态过载（6 套状态机 / 28 个状态值）

| 状态机 | 取值数 | 出处 |
|---|---|---|
| 项目状态 | 8（草稿…已驳回） | `enums.ts:79` |
| 阶段状态 | 3 | `enums.ts:113` |
| 质量门状态 | 5 | `enums.ts:115` |
| 里程碑状态 | 4 **+ `done` 布尔（双轨）** | `enums.ts:130` |
| 任务状态 | 5 | `enums.ts:141` |
| 健康度 | 3 | `enums.ts:100` |

用户原话"这么多状态的意义何在" —— **在项目详情一屏内，用户最多可同时看到 5 套状态机的 5 个标签**。

### A.3 三个痛点的代码级复核（含 1 项对用户认知的纠正）

| 痛点 | 用户描述 | 复核结论 | 证据 |
|---|---|---|---|
| **①** | 建项目要选里程碑 + 归属阶段 + 锚点，状态太多 | **属实，但比用户以为的轻**：A 类模板已自动预填 `stageCode`/`anchor`，用户不必填。真正的问题是「已经填好了却仍摆在表单上」——A 类 7 条里程碑 × 6 个控件 = **向导第 4 步一屏 42 个控件**，视觉负担 ≠ 填写负担，但用户无法分辨 | `ProjectCreatePage.tsx:82` 5 步向导；`:212-214` 模板预填锚点；`:724-814` 每行 6 控件 |
| **②a** | 里程碑无法新增 | **属实，且是硬缺失**：`ApiContract` 里**只有 `listMilestones` / `updateMilestone`，根本没有 `createMilestone` / `deleteMilestone`**。里程碑的唯一录入入口是「建项目向导第 4 步」，项目一旦创建，里程碑集合**永久冻结** | `api/contract.ts:201-202`；`MilestonesPage.tsx` 无新增按钮 |
| **②b** | 状态永远"未开始" | **属实，且比用户以为的更严重**：`milestone.status` 全仓**只有 2 个赋值点**——`index.ts:976`（用户手动勾"达成"复选框）与 `index.ts:1783`（变更单生效回写）。<br>🔴 **纠正**：用户以为「WBS 不绑里程碑所以状态不动」，实际是 **`wbs_nodes.milestoneId` 完全不参与里程碑状态计算——绑不绑都不会动**。UI 有个 `isOverdue` 补丁能显示"已逾期"，但**"进行中"这个状态永远不可能出现** | `index.ts:613`（初始 `'未开始'`）、`:976`、`:1783`；`MilestonesPage.tsx:326` |
| **③** | "工作分区"是啥？和"工作阶段"是不是一回事 | **是同一个东西**。上轮决策 D-4 把 WBS 节点 `nodeType='stage'` 的中文标签从「阶段」改成「工作分区」（`enums.ts:155`）。全仓 grep **「工作阶段」零命中**——用户记忆中的"工作阶段"就是改名前的「阶段」。<br>🔴 **改名反而加重了混乱**：改名后 WBS 表单里同时出现「工作分区」和「归属**生命周期阶段**」两个下拉，把"一个词两种含义"换成了"两个词并排摆着" | `enums.ts:151-156`；`WbsPage.tsx:342 / 432` |

### A.4 附带发现：系统术语与制度术语已错位

| 制度 §5.3 用词 | 制度含义 | 系统对应物 | 是否同名 |
|---|---|---|---|
| 阶段 | WBS 第 2 层容器 | `nodeType='stage'`（现称工作分区） | 曾同名，已改名 |
| 交付物 | WBS 第 3 层容器 | `nodeType='package'`（工作包） | ❌ 不同名 |
| **工作包** | **最底层、3-5 人日、有负责人有完成标准** | **`nodeType='task'`（任务）** | ❌ **同名异物** |

> 制度说「工作包 3-5 人日」，系统的粒度告警却打在 `task` 上（`rules.ts:268-275`，`GRANULARITY_LIMIT A:5`）。
> **即：制度的"工作包" = 系统的"任务"；系统的"工作包" = 制度的"交付物"。** 这是术语混乱的制度侧源头，光改前端文案治不了。

## B. 三个简化方案

### 方案一 · 极简：里程碑作唯一时间轴，WBS 退化为纯任务树

| 维度 | 设计 |
|---|---|
| **项目创建步骤** | **5 步 → 3 步**：①基本信息+分类判定（合并）②团队组建 ③确认提交。**里程碑步整体删除**，按模板静默生成，创建后在里程碑页调整。用户**零配置**：不选里程碑、不选阶段、不选锚点 |
| **WBS 结构** | **仍是树**，但节点类型 **3 类 → 2 类**：`group`（分组，可多级）+ `task`（任务，必为叶）。删除 `lifecycleStageId`；`milestoneId` 保留并接 UI。规则从 R-1~R-6 六条**砍到 2 条**：`task 必为叶`、`maxDepth=4` |
| **里程碑增删** | ✅ **补 `createMilestone` / `deleteMilestone`**。模板生成的标 `required=true` 不可删（保护制度必备节点），用户自建的可自由增删 |
| **里程碑状态** | 四态自动推导（口径见 §B.4）+ PM 手动覆盖。**不再依赖 WBS 绑定**：即使一个任务都没挂，也会随时间自然 未开始→进行中→已逾期 |
| **"阶段"怎么处理** | **UI 层彻底消失**。`project_stages` 表**保留但降级为质量门的挂载点**，不再向用户暴露"阶段"字样：概览的「生命周期阶段」条改名为「**质量门进度**」，推进按钮从「进入《设计》阶段」改为「**提交《QG3 设计门》检查**」 |
| 用户可见概念数 | **4**（里程碑 / 质量门 / 分组 / 任务） |
| ✅ 优点 | 心智最轻；WBS 表单从 8 个字段降到 5 个；三个痛点全部直接消解；术语只剩"分组/任务"两个无歧义词 |
| ❌ 缺点 | ① 「项目现在走到第几步」失去显式载体，只能用"已过 N 道门"替代，管理层看板需重做 ②「阶段顺序锁」与"阶段进度 rollup"两项衍生能力永久放弃 ③ 上轮 T-01/T-05/T-06 关于 `lifecycleStageId` 的成果基本作废 |
| 工作量 | **中**（删多于加：删 1 列 + 删 2 错误码 + 简化 childTypes；但概览页与 3 个页面需重做文案与信息架构） |

### 方案二 · 折中：阶段保留但全自动，用户零配置（**推荐**）

| 维度 | 设计 |
|---|---|
| **项目创建步骤** | **5 步 → 4 步**：①基本信息+分类（合并）②团队组建 ③**里程碑确认（只读预览 + 一个"改日期"入口）** ④确认提交。**归属阶段/锚点两个下拉从向导删除**，由系统按模板自动落锚（A 类已有映射）；B/C 类留空，创建后可在里程碑页补选。用户**零配置** |
| **WBS 结构** | **树不变，3 类节点不变**，但：① `requireStageBinding` **三类全改 false** —— 用户新建工作分区**不再必须选归属阶段** ② 阶段绑定只在**建项目骨架预生成时自动完成**（`index.ts:652-682` 已实现，无需改） ③ 用户手建的分区默认 `lifecycleStageId=null`，**取消黄色告警**（不绑就是不绑，不是错误） |
| **里程碑增删** | ✅ 同方案一：补 `createMilestone` / `deleteMilestone`，模板必备项锁删 |
| **里程碑状态** | 同方案一（§B.4）。新增里程碑时**归属阶段自动按日期落区间推断**，用户不填 |
| **"阶段"怎么处理** | **保留为后台脚手架**：仍是质量门载体、仍支持顺序推进、概览阶段条保留（这是管理层要的）。但在**创建向导和 WBS 表单里完全不出现**。删除 `anchor(start/mid/end)` 字段（制度无出处，见 §E） |
| 用户可见概念数 | **5**（里程碑 / 质量门+阶段合并展示 / 工作分区 / 工作包 / 任务）；**锚点消失** |
| ✅ 优点 | ① **用户可见复杂度与方案一几乎相同**（建项目同样零配置、WBS 同样不用选阶段），但**质量门与"当前阶段"指标零损失** ② 改动以"隐藏 + 补两个接口"为主，**不删表不删列**，上轮 14 个任务的成果全部保留 ③ 与制度 §7.1「质量门=阶段转换检查点」不冲突，制度改动面最小 |
| ❌ 缺点 | 概念数仍是 5 个（比方案一多 1 个）；「工作分区 vs 工作包」的重名困扰**不会自动消失**，必须靠 §D 的术语归一一起做，否则痛点③ 只解决一半 |
| 工作量 | **小~中**（补 2 个接口 + 状态推导函数 + 3 个页面减字段 + 删 `anchor`） |

### 方案三 · 双档：默认简单模式，PMO 可开专业模式

| 维度 | 设计 |
|---|---|
| **项目创建** | 默认走方案一的 3 步；PMO 在模板管理里可为某分类开启"专业模式"，走方案二的 4 步 |
| **WBS 结构** | 数据模型统一按方案二存；简单模式只是**隐藏** `lifecycleStageId` 字段与"工作分区"类型（只给分组/任务） |
| **里程碑** | 增删与状态推导两个模式完全一致 |
| **"阶段"** | 简单模式隐藏，专业模式显示 |
| ✅ 优点 | 既满足"太复杂"，又给 PMO 保留完整管控；可作为方案一/二的**灰度过渡壳** |
| ❌ 缺点 | ① **每个页面多一条 if 分支，测试面翻倍**（WBS 表单、向导、概览、里程碑页 ×2） ② 用户会问"为什么别的项目长得不一样"——**模式本身成为第 8 个要理解的概念** ③ 用户诉求是"更简单"，不是"更多选择"，方向性上与诉求相悖 |
| 工作量 | **大**（方案二 + 全链路模式开关 + 双份验收） |

### B.4 里程碑状态自动推导口径（三方案共用 · 回应痛点②b）

现状问题：`status` 只有人工触发的 2 个赋值点，且 `status` 与 `done` 布尔**双轨并存**。

**建议规则（自上而下，命中即定）：**

| 序 | 条件 | 结果 | 说明 |
|---|---|---|---|
| 1 | `statusOverride` 非空且未过期 | 用手动值 | **PM 可手动覆盖**，覆盖记审计，日期变更后自动失效 |
| 2 | `done = true` | 已达成 | 保留手动勾选达成 |
| 3 | `today > currentDate` | 已逾期 | 现 UI 已有此补丁，转正为引擎逻辑 |
| 4 | 关联任务完成度 > 0% **或** `today ≥ 起算日` | **进行中** | 🔴 **关键**：`起算日 = 上一里程碑的 currentDate`（首个取 `project.planStart`）。**即使零个 WBS 任务挂载，里程碑也会随时间自然进入"进行中"** |
| 5 | 否则 | 未开始 | |

**配套两条：**
- **关联任务完成度** = 直接/间接挂在该里程碑下的 `task` 节点，按 `estimateDays` 加权的 `progress` 平均（直接复用 `rules.ts:414 rollupProjectProgress` 算法，零新范式）。在里程碑页新增一列「关联任务 3/8 · 62%」，让用户看得见推导依据。
- **消除双轨**：`done` 退化为派生值 `done = (status === '已达成')`，不再作为独立可写字段。

## C. 推荐：方案二（折中）+ 强制配套三件事

### C.1 推荐结论

> **推荐方案二**，但**必须同时做** ①§B.4 状态自动推导 ②§D 术语归一 ③删除 `anchor` —— 三者缺一，痛点就只解决一半。

### C.2 理由（按"用户好理解好操作"排序）

1. **用户可见的简化幅度，方案二 ≈ 方案一。**
   用户抱怨的是**操作时看到什么**，不是数据库里有几张表。方案二做完之后：建项目**同样零配置**、WBS 建分区**同样不用选阶段**、里程碑**同样能自由增删且状态会动**。用户在界面上感受不到方案一与方案二的差别，**唯一差别是概览页多一条阶段进度条——而那恰恰是管理层想要的东西**。

2. **方案一会用"看不见的复杂度"换"看得见的简化"。**
   删掉阶段之后，质量门要挂在哪儿？上轮 PRD 已用模板数据证过：B 类 S3「评审」、S5「回顾」、C 类 S4「调试验收」都是**零里程碑阶段**，门无处安放，只能造假里程碑——那是把复杂度从 UI 挪到数据里，一年后又是一笔债。

3. **痛点③ 的根不在"阶段"，在"重名"。**
   用户问的是「工作分区和工作阶段是不是一回事」——这是**命名问题**，不是**结构问题**。删掉生命周期阶段并不能让"工作分区 vs 工作包"变清楚；反过来，只要做完 §D 的术语归一，即使保留阶段，用户也不会再问。**用结构手术解决命名问题，成本高且不对症。**

4. **方案三与诉求方向相悖。** 用户说"太复杂"，给他两套模式等于让他先做一道选择题。

5. **工程风险最低。** 方案二不删表、不删列、不改 `childTypes` 规则，上轮 43 个种子节点的迁移与校验成果全部有效，回归面可控。

### C.3 如果用户仍嫌不够简，退方案一的代价（供拍板参考）

| 放弃项 | 代价 |
|---|---|
| 概览「生命周期阶段」条 | 需重新设计为「质量门进度」，管理层看板口径变更 |
| 阶段顺序推进 + `E_STAGE_SEQUENCE` | 门控从"卡阶段"变成"卡节点"，制度 §7.1 需实质性改写 |
| 阶段进度 rollup | 无法回答"设计阶段完成了多少" |
| 上轮 T-01/T-05/T-06 部分成果 | `lifecycleStageId` 全链路作废 |

## D. 术语处理：一个词只留一个含义

### D.1 归一方案

| 现用词 | 现在指什么 | **建议** | 理由 |
|---|---|---|---|
| **生命周期阶段** | `project_stages` | 保留，但 UI 上**只在概览页出现一次**；建项目向导、WBS 表单、里程碑页一律不出现"阶段"字样 | 阶段是治理概念，PM 干活时不需要它 |
| **工作阶段** | 已不存在（旧标签） | — | 已改名，无需处理，但需在版本说明里告知用户"工作阶段已更名" |
| **工作分区** | `nodeType='stage'` | 🔴 **改为「分组」**（若采纳 Q4，与工作包合并为单一「分组」） | "分区"是生造词，用户零认知；"分组"是通用词，零学习成本 |
| **工作包** | `nodeType='package'` | 🔴 **与上者合并为「分组」**（靠层级区分，不靠类型区分） | 用户分不清分区和工作包，本质都是容器；合并后 `childTypes` 简化为 `group→[group,task]`、`task→[]` |
| **任务** | `nodeType='task'` | 保留 | 无歧义 |
| **锚点 start/mid/end** | `milestones.anchor` | 🔴 **直接删除** | 制度全文无此概念（"锚点"仅作修辞出现 3 次，均指里程碑本身）；纯实现产物，零用户价值，却占了向导 2 个下拉 |
| **归属阶段**（里程碑） | `milestones.stageId` | 字段保留（用于阶段进度聚合），**UI 改为只读展示**「所属：S3 设计」，不给用户下拉 | 由系统按日期自动落区间即可 |

### D.2 归一后用户要理解的词（**7 → 4**）

> **里程碑**（哪天要交什么） · **质量门**（过关才能往下走） · **分组**（活儿怎么归类） · **任务**（谁在什么时候干什么）

### D.3 一句话解释（建议直接用于 UI 引导 / 帮助文案）

> 项目按**里程碑**排时间轴，每个里程碑前有一道**质量门**要过；要干的活按**分组**归类，最小单元是**任务**；任务做完，里程碑自动往前走。

## 一句话总结

> **推荐方案二：把"阶段"降级为用户看不见的后台脚手架（建项目零配置、WBS 不用选阶段），同时补齐里程碑的增删接口与"随时间+任务完成度自动推导"的状态机，并把「工作分区/工作包」归并为一个「分组」、删掉毫无制度依据的「锚点」——用户要理解的概念从 7 个降到 4 个，建项目从 5 步降到 4 步且全程零配置，而质量门与阶段进度这两项管理层刚需一点不丢。**
