## 1. 产品目标

1. **G1 · 时间轴可信**：里程碑编号、排序、日期三者恒定自洽——用户在任何时刻看到的 M1..Mn 都严格等于按计划日期排列的先后顺序，不需要人工校对。
2. **G2 · 默认值即可用**：模板带出的默认里程碑必须落在项目计划周期 `[planStart, planEnd]` 之内，用户开箱即得一份可直接执行的时间计划，而不是一份需要逐条手改的错误草稿。
3. **G3 · 统计口径与视觉一致**：里程碑的「关联任务数」必须等于用户在 WBS 树中看到的挂载条目数，且「计数」与「钻取列表」严格同源，杜绝对不上账。

## 4. 关键产品决策

### A. 【问题 ④】关联任务计数口径 → **采用口径 Y，并做「计数/加权」分离**

**决策**：`milestoneTaskNodes(nodes, msId)` 的返回集合改为 **口径 Y = { 所有 `milestoneId === msId` 的节点 } ∪ { 这些节点各自子树中的真叶子 }，按 `id` 去重**。该集合是「关联任务」的**唯一真源**，同时供计数与钻取列表使用。

**三个口径的裁决理由**：

- **排除口径 Z**（只统计 `milestoneId === msId` 的节点）：这是**比现状更糟**的方案。经核实 `createProject` L655-681 只给顶层骨架 task 写入 `milestoneId`，用户后续新建的子任务 `milestoneId` 为 `null` 且不继承。采用 Z 会导致绝大多数里程碑的 `total` **恒等于 1**，无论用户挂了多少子任务。直接否决。
- **排除口径 X**（现状，只算子树叶子）：它制造了一个隐蔽的**语义漂移**——骨架 task 刚创建时自己是叶子，`total = 1`；用户拆出子任务的那一刻，顶层 task 从统计里"蒸发"，`total` 从 1 变成子任务数。用户的心智是「我做了拆分，工作变多了」，看到的却是一个和拆分前差不多甚至语义断裂的数字。用户反馈「数量还是不对」正是这种断裂的直觉表达。
- **采用口径 Y** 的正面理由：
  1. **顶层 task 是里程碑的合法工作载体**。它不是虚构的分组容器——是引擎在 `createProject` 时**主动生成并绑定 milestoneId** 的骨架节点，承载着「这个里程碑要交付什么」。把它排除在外，等于系统否认自己生成的东西。
  2. **与用户视觉一致**。用户在 WBS 树里看到 M3 下面有 1 个顶层任务 + 4 个子任务共 5 条，里程碑页就应该显示 5。所见即所数，是统计类 UI 的第一性原则。
  3. **消除"未关联"误导**。现状下一个已经排了满满 4 个子任务的里程碑，如果这些子任务恰好没绑 milestoneId 而只有父绑了，会显示"未关联"。口径 Y 通过子树下钻覆盖这种情况。

**关于计数与加权的分离（这是本决策的关键约束，请工程侧务必落实）**：

| 指标 | 口径 | 理由 |
| --- | --- | --- |
| `total` | 口径 Y 集合大小 | 用户心智 = 条目数 |
| `done` | 口径 Y 集合中 `progress >= 100` 的数量 | 与 total 同集合，自洽；父节点 100% 恰好意味着子全完成，不会矛盾 |
| `progress` | **仅对 Y 集合中的真叶子**做 `estimateDays` 加权 | 父节点 `progress` 是汇总值，参与加权即**重复计权**；且骨架 task 的 `estimateDays = 0`（权重回落为 1）、`progress` 长期为 0，若计入会**永久性拉低**整碑完成度。这是数学正确性要求，不可妥协 |

**钻取弹窗（`openDrill`）展示内容**：展示 `milestoneTaskNodes()` 返回的**完整 Y 集合**，条目数与列表数字逐一对应。父节点渲染「汇总」Chip、不展示工时权重、子节点缩进一级。弹窗顶部加一行说明：「共 N 条关联任务；完成度按叶子任务工时加权计算，汇总节点不计入权重。」——用一句话消化掉「5 条里完成 3 条却显示 80%」的疑问。

> 契约影响：`MilestoneTaskStats` 三字段（total / done / progress）**不变**，仅语义修订。`src/types/project.ts` L248 的注释「关联子树内真叶子总数」需同步改为「关联节点数（直接绑定节点 ∪ 其子树叶子，去重）」。工程改动集中在 `src/utils/wbs.ts` 两个函数 + `MilestonesPage` 钻取渲染，范围可控。

### B. 【问题 ②】默认里程碑超期 → **采用策略 α（等比压缩），并补齐边界规则**

**决策**：在项目创建路径（向导预填 + 引擎兜底）统一按下述算法生成里程碑日期。

```
planDays     = diffDays(planStart, planEnd)
templateSpan = max(所有 offsetDays)

若 planDays >= templateSpan:
    date = addDays(planStart, offsetDays)          // 不压缩，保持模板绝对节奏
否则:
    ratio = planDays / templateSpan
    date  = addDays(planStart, round(offsetDays × ratio))
```

**边界规则（必须实现，逐条验收）**：

1. **首碑允许与 planStart 同日**。`offsetDays = 0` 的里程碑（如「项目立项」）压缩后落在 `planStart` 是**正确语义**，不是缺陷——立项本来就发生在开工日。
2. **非首碑不允许被压到 planStart**。若 `offsetDays > 0` 但 `round(offsetDays × ratio) === 0`，强制取 `1`（即至少 `planStart + 1 天`）。理由：一个有实质交付物的里程碑落在开工当天，会让「未开始 → 进行中 → 已达成」的状态推导在项目第一天就全部触发，时间轴退化为一个点。
3. **保证严格单调不减**。压缩后若某碑与前一碑同日，后碑顺延 1 天，且顺延后不得超过 `planEnd`。
4. **末碑恰好落在 planEnd**。`offsetDays === templateSpan` 的碑压缩后 = `planEnd`，这是等比压缩的天然性质，也是用户最直观的正确性锚点。
5. **极端周期兜底**：当 `planDays < 里程碑数 - 1` 时规则 3 无法满足，此时**允许同日堆叠**，但必须触发 P1-M12 的非阻塞警告，**绝不阻断项目创建**。产品立场：系统不替用户否决一个"三天做完七个里程碑"的荒唐计划，只负责把风险说清楚。

**为什么不选 β / γ**：

- **β（截断 + 提示）**被否决：clamp 会让多个里程碑**堆在 planEnd 同一天**，时间轴退化成一个点，甘特/概览页全部失真。它把"日期越界"这一个问题换成了"日期重复且节奏丢失"这一个更难修的问题。
- **γ（保持绝对偏移 + 标红）**被否决：这是把系统的责任推给用户。默认值一生成就是错的，还要用户手动改 7 次——这与产品目标 G2「默认值即可用」直接冲突。**但 γ 的预警思路有价值，已降级为 P1-M13 的运行期预警**：创建期用 α 保证正确，运行期若用户自己改期改越界了，再标红提醒。二者分工明确，不冲突。

**压缩后允许与 planStart 同日吗？** —— **首碑允许，非首碑不允许**（见边界规则 1、2）。这是明确表态，不留模糊。

### C. 【问题 ③】编辑范围 → **三字段可编辑，达成状态留在列表，允许删除任意里程碑**

**可编辑字段清单**：

| 字段 | 是否可编辑 | 说明 |
| --- | --- | --- |
| `name` 名称 | ✅ 编辑弹窗内 | 必填校验，trim 后不得为空 |
| `target` 目标 / 达成标准 | ✅ 编辑弹窗内 | 多行文本，允许清空 |
| `currentDate` 当前计划日期 | ✅ 编辑弹窗内 | **沿用单向规则**：提前直改生效，延后抛 `E_MS_NEED_CHANGE` 并引导变更单。与现有独立改期入口共用同一条 `updateMilestone` 通路（现有改期入口保留，作为高频操作的快捷方式） |
| `baselineDate` 基线日期 | ❌ 只读展示 | 单向规则的基石，任何路径都不可修改 |
| `required` 必备标记 | ❌ 不可编辑 | 它是模板契约的锚点，是"这个碑来自哪个模板规范"的血缘信息，不应由项目侧随意翻转 |
| `status` 状态 | ❌ 不可直接编辑 | SK-2：派生值。需要人工干预时走已有的「人工覆盖」入口 |

**达成状态是否允许在列表直接勾选？—— 允许，且必须继续留在列表列，不放进编辑弹窗。**

理由：「标记达成」是一个带审计留痕、会写 `doneAt` / `doneBy`、会清空 override 三元组的**状态动作**，不是资料编辑。把它塞进编辑表单会让「保存」按钮的语义变得危险——用户本想改个错别字，点保存却顺手把里程碑标成了已达成。**动作与编辑必须在 UI 上物理分离**，这是不可退让的交互原则。现状的列表 Checkbox 形态是正确的，保持不动。

**是否允许删除里程碑？—— 允许删除任意里程碑，包括模板必备碑。**

依据与约束：
- 引擎侧已解耦（`deleteMilestone` L980 注释明确「里程碑可自由删除，不再因『必备』锁删」），前端删除按钮也未按 `required` 禁用，两侧已一致，本次只需**补强确认文案**（P1-M13）。
- 删除语义保持现状：级联删除其质量门与检查项；WBS 关联节点**只解绑不删任务**（`milestoneId` 置 null）——绝不因删一个碑而丢掉用户的工作量记录，这条底线不变。
- 前端保留 `E_MS_REQUIRED_LOCKED` 的 catch 分支，兼容真实后端可能仍启用锁删策略的情况。

### D. 【问题 ①】编号规则 → **确认「按 currentDate 升序重排为 M1..Mn」为预期且正确的行为**

**决策：确认。** 该行为写入验收标准，作为里程碑编号的**唯一规则**。

产品定义：**M 编号是时间轴上的序号，不是身份标识。** 它回答的是「这是项目的第几个里程碑」，而不是「这是哪一个里程碑」。身份由 `id` 承载，WBS 节点通过 `milestoneId` 关联，重排不影响任何引用完整性（`renumberMilestones` L251 注释已确认这一点）。因此**插入即重排、删除即重排、改期即重排**是完全正确的，用户不应该、也不需要拥有一个"编号不随日期变化"的里程碑。

**必须补齐的触发点（当前实现有缺口）**：

| 触发路径 | 现状 | 要求 |
| --- | --- | --- |
| `createMilestone` | ✅ 已调用（L957） | 保持 |
| `deleteMilestone` | ✅ 已调用（L995） | 保持 |
| `updateMilestone` 改期成功后 | ❌ **未调用**（L1031-1039） | **必须补** —— 这是问题 ① 用户走查仍失败的主因 |
| 变更单审批回写里程碑日期后 | ❌ 未调用 | **必须补** |
| `createProject` 生成默认里程碑后 | ❌ 未调用（L618-648 直接用模板 `md.code`） | **必须补** —— 用户在向导里改过日期或新增过碑，模板 code 顺序即失效 |
| `milestonesWithGate` 读取时 | ❌ 未调用 | **必须补**（P0-M2）—— 幂等重排，自动修复 localStorage 中的历史脏数据 |

**验收标准（写入 P0-M1 / P0-M2）**：
1. 现有 M1(3/1) M2(3/10) M3(3/20)，插入日期 3/15 的新碑 → 结果为 M1(3/1) M2(3/10) **M3(3/15)** M4(3/20)，**不得出现 M5**。
2. 把 M4(3/20) 改期提前到 3/5 → 立即重排为 M1(3/1) **M2(3/5)** M3(3/10) M4(3/15)。
3. 删除 M2 → 剩余里程碑重排为连续的 M1..M3，无空号。
4. **不清 localStorage**、直接刷新页面，历史脏编号自动修正。
5. 连续刷新 10 次，编号稳定不抖动（幂等性验证）。

> ⚠️ 给工程/QA 的提醒：问题 ① 复现与验证时，请**先清空 localStorage 中的 mock DB 再重跑一遍**，然后**再用不清缓存的方式验证 P0-M2 的读路径自愈能力**。两种场景都要过，否则会误判修复效果。
